> 结论先行：**不要引入 Blender 建模流程**。本项目的渲染器与美术资产是"代码即模型"，改造收益与风险严重倒挂。

## 〇、先说结论（三条）

| 判断 | 依据 |
|---|---|
| **① 当前架构不适合接 glTF/Blender 资产** | 渲染器是自研 **Canvas 2D 透视投影**（`render.js` 头部自述"轻量 3D 渲染器"），无 WebGL、无 three.js、无 z-buffer、无骨骼动画系统。导入 glTF 等于**换渲染栈**，不是"加模型" |
| **② 导入模型的真实成本 ≈ 重写渲染层** | 需新增 WebGL 上下文 + 模型加载 + 蒙皮动画 + 与现有画家算法排序共存；而 `render.js` 有 **4 份字节级镜像副本**（红线 2），改造面 ×4 |
| **③ 收益点不在"模型精度"，在"读球性"** | 乒乓球游戏的可玩性由**球的轨迹可读性、击球反馈、镜头**决定，不由角色多边形数决定。当前角色是火柴人，本身就是**有意的风格化选择**，换成写实模型反而降低可读性 |

**因此本文的核心建议是：把"建模"预算转投到"程序化几何增强 + 表现层反馈"**，用现有 Canvas 管线就能拿到 80% 的观感提升，且零新增依赖、零镜像风险。

## 一、现状审查（事实与数据）

### 1.1 渲染架构

```
Canvas 2D  ← 单 <canvas id="game">，无 WebGL 上下文
   ├─ Camera：手写 look-at + 透视除法（project(): s = f/z）
   ├─ 原语：limb(胶囊) / box(六面体) / poly(多边形) / line
   ├─ 排序：**画家算法**（手工安排绘制顺序），无深度缓冲
   └─ 缓存：观众席静态层 / 动画层 两张离屏 canvas，相机或尺寸变化才重建
```

**关键约束（决定了方案边界）**：

- **没有 z-buffer** ⇒ 任意两个半透明/相交物体都会穿帮。`drawScene` 里靠注释手工排序（"对手先画，球台表面盖住其腿部"）。**任何新增几何都必须手工插进这条排序链**，这是接模型最大的隐性成本。
- **没有骨骼动画系统** ⇒ `characters.js` 是自建骨架（髋→脊柱→肩→颈→头 + 弹簧阻尼平滑），动画由**物理参数驱动**（步幅、挥拍动量）。glTF 的蒙皮动画无法直接复用这套驱动逻辑。
- **单 canvas、无后处理** ⇒ 无 bloom/SSAO/阴影贴图。`drawTableShadow` 是手绘椭圆。

### 1.2 资产现状

| 项 | 实况 |
|---|---|
| `.blend` / `.glb` / `.gltf` / `.fbx` / `.obj` | **0 个**（全仓扫描） |
| three.js / babylon / WebGL | **未引入**（`package.json` 零运行时依赖，这是项目卖点） |
| 现有美术 | 全部**程序化生成**：球台/网/球/观众/看台/地板都是代码画的 |
| 镜像副本 | `render.js` ×4（`public` / `dist/ecs` / `android/assets/www` / `安装包/game`）、`app/render.js` ×4 |
| ITTF 尺寸 | 已精确对齐：台 2.74×1.525×0.76、网高 0.1525、球半径 0.02、台厚 0.035 |

### 1.3 性能与画质现状（已有成熟机制）

- **三档画质**（高/中/低）：高画质 dpr 不封顶；中画质电脑 1920p / 手机宽 750p；低画质电脑 1080p / 手机宽 400p。
- **手机高画质 dpr 封顶 2**（v2.4 为释放填充率）。
- **观众席双层离屏缓存**：静态层（地板+看台+静止观众）只在相机/尺寸/DPR/模式变化时重建；动画层单独烘焙。
- **观众密度自适应**：满员 / 0.5 / 0.25 三档。
- **低画质关闭溅射粒子、保留尾影主轨迹**。

> 这套机制说明：项目**已经在为填充率做精细预算**。任何提高几何复杂度的改动，都必须先回答"在手机 400p 档上还跑得动吗"。

### 1.4 门禁现状（改动必须满足）

- `npm run test:all` = **31 项测试 + 1 项引擎镜像校验**（`&&` 串行共 32 条命令；AGENTS 写的"32 项测试"略不精确，第 32 条是 `tools/check-engine-sync.js` 而非测试）。其中渲染相关：`browser-smoke`（DOM/Canvas 桩内跑全部前端脚本）、`crowd-*` 5 项、`seated-crowd`、`ws-skin`。
- **既有 2 项失败**（`physics-boundary-test`、`browser-smoke` 虚线勾选框），AGENTS 明确"与基线一致即视为无回归"。
- 红线 2：引擎镜像**字节级一致**，改完必须 `node tools/autosync.js --once` + `test:sync`。
- 红线 6：**只改排版时不许动玩法**（`aiLevel`、队伍槽位、localStorage 键、服务端接口）。

## 二、为什么"Blender 建模 → 导入引擎"在本项目不划算

把这件事拆成必须依次跨过的 6 道坎，每道都有具体代价：

| # | 坎 | 具体代价 | 风险 |
|---|---|---|---|
| 1 | **渲染栈** | 引入 WebGL（原生或 three.js）≈ 新增 600KB+ 依赖，破坏"零依赖"卖点；或手写 WebGL 渲染器（约 2000+ 行） | 高 |
| 2 | **模型管线** | 需 glTF 加载器（解析 + Draco 可选）、材质映射、纹理图集；APK 体积增加（当前 4.5MB 级，红线 8 对下载体验敏感） | 中 |
| 3 | **动画** | glTF 骨骼动画无法直接接现有物理驱动骨架 ⇒ 要么重做动画层，要么把现有 IK 结果**烘焙成骨骼动画**（本末倒置） | 高 |
| 4 | **排序** | 失去画家算法的可控性，必须真做 z-buffer；但 WebGL 与现有 Canvas 2D 特效层（尾影/溅射/虚线）混用需双上下文或全量迁移 | 高 |
| 5 | **镜像 ×4** | `render.js` 4 份副本 + `autosync` + `test:sync`；任一处漏同步 = 门禁红 | 中 |
| 6 | **门禁** | `browser-smoke` 用 **Canvas 2D 桩**跑前端；换 WebGL 后桩失效，等于重写该测试（69KB） | 高 |

**结论**：6 道坎里有 4 道是"高"，且第 1、6 道会连带摧毁项目现有的两个核心资产——**零依赖**与**可测试性**。

> 补充：这个项目的美术定位本来就是**风格化火柴人**（README 与 `characters.js` 头部都明确"火柴人物理骨架"）。写实乒乓球角色在 2.5D 透视 + 手机小屏下，**辨识度反而下降**（看不清挥拍相位、看不清球拍角度）。**风格化不是妥协，是这个玩法的正确解。**

## 三、推荐方案：不碰 Blender 的三阶段观感升级

目标：在不新增依赖、不改镜像结构、不破门禁的前提下，把"看起来更好"做实。

### 阶段 A · 程序化几何增强（1~2 天，风险低）

全部在 `render.js` 现有原语内完成，**不新增文件**（避免动 `load-order` 与镜像清单）。

| 改动 | 做法 | 预期收益 |
|---|---|---|
| **球台质感** | `drawTable` 增加台面渐变 + 边缘高光条 + 台腿接地阴影（现为纯色块 + 手绘椭圆） | 立体感立刻上一个档次 |
| **球网** | 网面改为**双层网格线 + 顶部白边**（现为单层），网柱加圆柱高光 | 近景细节 |
| **球体** | `drawBall` 增加**随速度变化的运动模糊拉长**（已有 trail，可复用其采样）+ 高光点位移 | 高速球更"有劲" |
| **地板反射** | 台面下缘加一条**低透明度倒影**（纯 2D 渐变，非真反射） | 球馆氛围 |
| **观众** | 现有 `seatedPose` 增加**分排明暗**（远排更暗） | 空间纵深 |

> 关键：这些改动**只改绘制内部实现，不改任何函数签名**，因此 `browser-smoke` 与 `crowd-*` 测试全部不受影响。

**可行性已核实**：`render.js` 已导出 `shade`（十六进制调色）、`poly`（多边形填充+描边）、`line`（带宽度线段）、`box`（六面体）、`limb`（胶囊）五个原语，且都在 `return { ... }` 的对外契约里。上述质感增强**全部可用这些原语拼出**，无需新增导出、无需改 `characters.js`。

具体到「台面渐变」一条：`drawTable` 现在用 `box()` 画整块台面（纯色）。改为在台面四点投影后，用 `ctx.createLinearGradient` 沿投影后的短轴做渐变，再叠 `poly()` 描边——**仍在 Canvas 2D 内，无新依赖**。

### 阶段 B · 表现层反馈（2~3 天，风险低）

| 改动 | 做法 | 收益 |
|---|---|---|
| **击球顿帧** | 命中瞬间 2~3 帧时间缩放（0.15×）+ 屏幕微震 | 打击感（成本极低、体感提升最大） |
| **球拍轨迹残影** | 复用 `drawTrail` 的采样机制，对**拍面**而非球做短残影 | 挥拍可读性 |
| **落点预判圈** | 已有 `drawServePath`，扩展为"对手回球落点圈"（仅高画质） | 新手友好 |
| **得分瞬间镜头** | `Camera.set` 已有插值能力，加一次 0.3s 推近 | 情绪节奏 |
| **旋转可视化** | 球体纹理（已有马格努斯旋转物理）改为**随旋转方向偏移的高光** | 让"旋转"这个核心机制可见 |

> 阶段 B 全部是**加法**（新增绘制调用），不改现有调用链，风险极低。

### 阶段 C · 若要"角色升级"，用**程序化换装**而非建模

`dressup.js` 已有装扮方案系统（尾影/溅射），但**角色外观无槽位**。建议：

1. 在 `characters.js` 的 `STICK` 配色表基础上，抽出 **`SKIN` 描述结构**（头型/上衣/拍面/球衣条纹），全部用现有 `limb`/`box` 画。
2. 新增 4~6 套"皮肤"（如 条纹球衣、护腕、发带），仍是火柴人骨架，**零新增几何原语**。
3. 皮肤数据可进 `localStorage`（与 `dressup` 同机制），**不动服务端**。

> 这条路能拿到"个性化"的全部收益，而成本是阶段 A/B 的零头。**它才是"建模"需求真正想要的东西**。

## 四、如果坚持要 Blender：最小可行接入路径（仅作备选）

若美术方向已定、必须上真模型，给出**代价最小**的做法（仍不推荐，但比"直接上 three.js"理性）：

1. **只替换"角色"，不替换场景**。球台/网/地板保持程序化（它们本来就是精确 ITTF 尺寸，模型化毫无收益）。
2. **模型规格硬约束**（写进交付单，避免美术返工）：
   - 格式 **glTF 2.0 binary (.glb)**，单文件 ≤ 300KB
   - 三角面 ≤ 3000/角色，**单一材质图集 1024×1024**
   - 骨骼：与 `characters.js` 现有骨架**一一对应**（髋/脊柱/肩/颈/头/双腕/双膝/双足），命名固定
   - **不导出动画**（动画由现有物理驱动，导出反而要重做驱动）
3. **渲染接入**：新增 `render-webgl.js` **与** `render.js` 并存，用开关切换；`drawScene` 保持同一对外签名。
4. **必须同步的 4 处**：`public` → `dist/ecs` → `android/assets/www` → `安装包/game`，跑 `autosync` + `test:sync`。
5. **门禁补救**：`browser-smoke` 的 Canvas 2D 桩对 WebGL 无效，需为 WebGL 路径单独加"无异常"冒烟（否则等于放弃该测试的覆盖）。

**这份清单本身就是"不推荐"的证据**：一个 ≤3000 面的角色，换来 5 项工程改造 + 1 项测试重写。

## 七、附：本方案的三个"不做"

1. **不做**"场景模型化"——球台/网/地板已是精确 ITTF 尺寸的程序化几何，模型化只会引入误差与体积。
2. **不做**"角色写实化"——火柴人是**玩法可读性的载体**，写实化会牺牲挥拍相位与拍面角度的可辨识度。
3. **不做**"为建模而换渲染栈"——那会同时摧毁项目的零依赖与可测试性两个核心资产。
