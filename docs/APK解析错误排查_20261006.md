# 安卓版 APK「解析包错误」排查留痕（2026-10-06）

> **本文档为历史排查记录，正文中的 v310 与其字节数/指纹均为当时的事实，不再更新。**
> 当前发布版本见 `package.json`（版本号单一真源），对外文件名 = `PingPongDuel-v<version 紧凑串>.apk`。
>
> **「解析包错误」在本项目已知的两个成因**（排查时先分清是哪一个）：
> 1. **线上文件残缺** —— 本文档记录的那次：CDN 上那份比本地产物少几百 KB。
> 2. **链接指向不存在的文件名** —— 请求落到 SPA 回退，返回 **200 + HTML**，
>    用户下到一个改名为 `.apk` 的网页，系统按「不是安装包」拒绝。
>    该文件名此前散落三处手工维护（`download.html` / `_headers` / `index.html`），已全部收口到
>    `tools/set-version.js`；`download.html` 另有 `deploy.yml` 发布前交叉校验兜底。
>    另见 `修改记录.md` 2026-10-06 v3.2.0 条目（CI 曾硬编码 `v301`，冒烟校验的还是下载页不引用的那个名字）。

---

> 现象：手机上安装 `PingPongDuel-v310.apk` 报「解析包错误 / 应用未安装」。
> 结论：**不是签名问题，是线上那份 APK 文件残缺**。已修复。

---

## 一、真正的病因

| 对象 | 字节数 | 判定 |
|---|---|---|
| 本地产物 `public/PingPongDuel-v310.apk` | 3,596,822 | 完整 |
| 线上 `ping-pong-duel.pages.dev/PingPongDuel-v310.apk`（修复前） | **3,155,776** | **少 441 KB，残缺** |
| 线上（修复后） | 3,596,822 | ✓ 与本地一致 |

APK 是 ZIP 容器，**文件尾部的中央目录（Central Directory）记录了全部条目索引**。
缺失尾部 → 安装器解不开索引 → 直接抛「解析包错误」，**与签名、与设备系统版本都无关**。

残缺文件的成因：Cloudflare Pages 边缘缓存里存着上一次未完整上传的对象；
本次 `wrangler pages deploy` 提示 `Uploaded 0 files (36 already uploaded)`，
即「内容哈希未变」而跳过了实际上传，但重新发布后线上对象已恢复为完整文件。

## 二、关键坑：`v1=false` 是**误判**，不要再重复排查

初查 `apksigner verify -v` 输出：

```
Verifies
Verified using v1 scheme (JAR signing): false← 误导
Verified using v2 scheme (APK Signature Scheme v2): true
Verified using v3 scheme (APK Signature Scheme v3): true
```

当时据此判断「v1 未生效 → 老设备装不了」。**这是错的。**

`apksigner verify` 默认按 `--min-sdk-version` 口径验证。本项目 `AndroidManifest.xml`
**没有声明 `minSdkVersion`**，验证口径落在 API 24+，该口径下走 v2 通道，
**v1 根本不参与判定**，于是报 `false`——这与 v1 签名是否有效无关。

改用 API 21 口径复验（`--min-sdk-version 21`，即真正会走 v1 的老设备口径）：

```
Verifies
Verified using v1 scheme (JAR signing): true   ← 实际有效
Verified using v2 scheme: true
Verified using v3 scheme: true
```

包内 `META-INF` 三个签名条目也完整：

```
META-INF/PPD.SF       4,321 B
META-INF/PPD.RSA      1,301 B
META-INF/MANIFEST.MF  4,194 B
条目总数 46
```

**结论：v1 + v2 + v3 三种签名全有效，Android 5.0~ 最新版本都能装。**

> 以后排查签名，一律用 `apksigner verify --min-sdk-version 21 -v` 看全口径，
> 不要拿默认口径的 `v1=false` 当结论。

## 三、本次实际改动

| 文件 | 内容 |

| `public/download.html` | 「提示解析包错误 / 安装包无效」排障段：加字节数 + SHA-256 自查法；下载步骤补全预期大小 |

`public/_headers` 早已配好（`Content-Type: application/vnd.android.package-archive`、

## 四、发布后如何快速验完整性（不必下载全包）

Pages 对 `HEAD` 不返回 `Content-Length`，改用 GET 取尾部几十字节：

```bash
curl -s -D - -o nul -r 3596000-3596821 \
  https://ping-pong-duel.pages.dev/PingPongDuel-v310.apk | findstr Content-Length
```

期望输出 `Content-Length: 3596822`。秒级完成，不受网速影响。

（服务器未按 Range 返回 `206` 而是 `200`，但 `Content-Length` 仍准确，
足够用于判断完整性。）

## 五、给用户的自查口径

下载后文件**必须**满足：

```
大小3,596,822 字节
SHA-256  A5B7AED916EF58E2230ADAC7BA7A324042C271CDB153A8DFE02F3985EFA336DA
```

任一不符即为残缺文件，**必然报解析错误**，需重新下载。

## 六、遗留风险

服务器不支持分段下载（Range 返回 200 而非 206），3.6 MB 在弱网下仍有中断风险，
中断即残缺。根治方向是减小体积：`assets/www/audio/music.mp4` 原始 3,352,708 B
占了整包的 93%，转成 opus/ogg 或降码率可显著降低失败率。
